# Tile resize: boundary-move, axis-dependent grow/elastic, teleport-during-drag

A tiled window resized by dragging its edge/corner moves **exactly one column/row boundary** (the tmux "1b" model, not translate-the-neighbors). On the **unbounded horizontal axis** the shrinking neighbor clamps at `min_column_width_px` and the canvas extends (grow); on the **bounded vertical axis** the edge overshoots during the drag and snaps back on release (elastic pin), because Win32 owns the dragged window's geometry during a native move-size and cannot be restrained live. Every window moved during the drag is **teleported** (instant `SetWindowPos`, bypassing the animator); the animator runs **only on release** — the same free-during-drag / commit-on-release split the translate drag already uses (`docs/src/dev-guide/tile-drag.md`, `src/daemon/drag.rs`).

## Context

flow-wm already resizes columns via the keyboard (`expand`/`shrink`, snapped to a slot ladder) and via IPC (`set_column_width`, free-form), but **dragging a tiled window's edge** enters the same `MoveSizeStart`/`End` lifecycle the translate drag uses and is misrouted into drop-zone detection. The data model already supports free-form geometry — `Column.width_px` and `Row.height` are per-element pixels (`src/layout/types.rs`) — but there is no resize drag state, no anchor-edge concept, and no row-height resize primitive. The hook cannot tell translate from resize (UI-Automation `MoveSizeStart` carries no sizing edge), and it cannot restrain a native move-size live, so the design has to fit the existing event-based hook plus the translate drag's established "dragged element follows the cursor freely; flow commits on release" pattern.

## Considered Options

- **Translate-neighbors ("1a") instead of boundary-move.** Rejected: the vertical axis is bounded to the work area (`src/layout/projection.rs` stacks rows verbatim; `src/workspace/y_offset.rs` is workspace-parking, not vertical scroll), so growing one row *must* steal from another — only boundary-move is possible vertically. Consistency picks boundary-move on both axes, which also makes a corner-drag one mechanism composed on two axes rather than two different models stitched at the corner.
- **Hard pin at the ceiling.** Rejected: restraining a native move-size live needs `WM_SIZING` subclass interception or a flow-wm-owned gesture — neither fits the event-based hook. Elastic is *forced* for native edge-drag, and we keep it uniform for any future owned gesture (alt-drag) so resize semantics stay trigger-independent (the "inconsistent animation" argument). Hard pin also fights the translate drag's free-during-drag precedent: the dragged element is never restrained live; it snaps on release.
- **Live snap-to-grid.** Rejected: a live snap fights the cursor (the edge jumps off it) and contradicts the documented "drag-resize is free-form (not snapped to the slot ladder)" principle in `src/layout/mutations.rs` — grid snapping belongs to the keyboard `expand`/`shrink` commands. The proposed "combined width = k·column_shift" grid also does not coincide with the per-column ladder: two on-ladder columns sum to a multiple of `column_shift` only when the gap is zero.
- **Animate during the drag.** Rejected: the animator's `RetargetFromCurrent` policy resets on every retarget, so per-pixel continuous targets stall the reflow (the bug `should_submit_preview` works around for translate); and tween lag would split the moving boundary from the cursor, breaking the "one boundary moves" feel. Resize is direct-manipulation — instant beats smooth (tmux/nvim resize instantly).

## Consequences

- **One boundary moves; the neighbor clamps then rides.** Dragging an edge shifts that one boundary. The growing side takes `+Δ`; the shrinking neighbor takes `−Δ` down to its minimum, then becomes a rigid rider. Horizontal past the minimum **extends the canvas** (columns beyond translate away from the grip); vertical past the derived maximum **overshoots and snaps back** (no canvas to extend into). The dragged edge tracks the cursor 1:1 throughout; only the count of other moving windows changes at the transition.
- **Elastic is uniform across triggers.** Native edge-drag cannot restrain → elastic. Any future flow-wm-owned gesture (alt-drag) must *deliberately reproduce* elastic (simulate overshoot + snap-back) so resize feels the same regardless of how it is grabbed.
- **Teleport during the drag, animate on release.** Resize reuses the existing direct path (`FlowWM::teleport_workspaces` / `registry::win32::set_window_rect` + `Border::set_geometry`) — it is a new *caller*, not a new placement function. On release, `animate_layout` runs once and includes the dragged window (it snaps from overshoot to its ceiling); neighbors are already at their clamped targets and do not re-animate. The "two ways to place a window" (animate vs. teleport) already exists and is justified by the same `RetargetFromCurrent` reset in both bystander-workspace switches and continuous resize.
- **New resize drag state, distinct from the translate `DragState`.** Entered only for `Tiling(Active)` windows, classified translate-vs-resize (and which edge) by a cursor-vs-rect hit-test at `MoveSizeStart`, since the hook carries no sizing edge.
- **New `min_row_height` config.** Only `min_column_width_px` exists today; the vertical floor needs its row analog (config field + clamping in the mutation layer), with the derived ceiling `max_row_height = available − (n−1)·min_row_height − inter-row gaps`.
- **`min_column_width_px` / `abs_max_width` are unchanged** and remain the horizontal floor/ceiling; the horizontal elastic fires at `abs_max_width`, symmetric to the vertical elastic at the derived max.
