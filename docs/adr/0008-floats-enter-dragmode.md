# Floats enter `DragMode` to suppress focus-follows-mouse (boundary reversal)

**Status:** Accepted — reverses the previously documented drag-module boundary ("floating windows never enter `DragMode`"). The boundary was stated in the `drag.rs` module doc and in `docs/src/dev-guide/tile-drag.md`; this ADR records the deliberate reversal so it stays discoverable, and those docs have been updated to match.

Floating windows now participate in `drag_state` for the whole `MoveSizeStart`→`MoveSizeEnd` window via a new `DragMode::Float` variant, so the singular invariant — *"`drag_state` is occupied ⇒ focus-follows-mouse and edge-hover-scroll stand down"* — covers floats automatically. No new suppression logic is added at the hover seam: the three hover entry points (`poll_hover`, the focus-dwell fire, the edge-dwell fire) already gate on `drag_state.is_some()`, so a float that owns `drag_state` suppresses FFM and edge-scroll for free. Implemented by ticket #26 (already merged into the parent branch); this ADR records the decision.

## Context

`drag_state` is FlowWM's interaction-state field: a single `Option<DragMode>` on the orchestrator that the hover subsystem keys off to decide whether FFM (and edge-scroll) are live. The rule "`drag_state` occupied ⇒ FFM/edge-scroll suppressed" was already the one mechanism by which tile translate and tile resize disabled hover during a native move-size gesture. The drag-module doc, however, asserted a hard boundary: *floating windows never enter `DragMode`* — a float's `MoveSizeStart` was an early-return in `on_drag_start`, and the float's `LOCATIONCHANGE` events kept routing to the passive float-sync path (`on_float_location_changed` → `store_float_rect`), so nothing suppressed FFM during a float's move-size window.

That boundary was disproved by the bug behind [#24](https://github.com/CCpcalvin/flow-wm/issues/24): while the user resizes a float by dragging its edge (or drags it by its title bar), fast pointer motion flings the cursor onto a neighboring tile. With FFM still live, the hover subsystem focuses that tile mid-gesture, which pushes the OS foreground onto the tile and aborts the native move-size. The gesture feels broken under fast motion. The root cause — confirmed from `debug.log` — is a `hover focus` foreground push firing *inside* a `MoveSizeStart`→`MoveSizeEnd` window for a float, exactly the failure the tile path avoids by occupying `drag_state`. See also the float-tile stacking invariant in [ADR-0003](0003-float-tile-stacking-invariant.md) and the tile-resize contract in [ADR-0004](0004-tile-resize-contract.md), which already rely on the `drag_state`-suppresses-hover rule for their own parts of the move-size lifecycle.

## Considered Options

- **A parallel `MoveSizeStart`/`MoveSizeEnd` gesture flag for floats (a twin of `drag_state`).** Rejected: it splits the suppression rule into two — "`drag_state` occupied ⇒ suppress" *and* "float-gesture-flag set ⇒ suppress" — and forces every hover entry point to learn about a second field. The existing tile-path precedent already pays the cost of one field; reusing it keeps the rule singular and removes any chance of the two flags drifting out of sync.
- **Add a new suppression guard at the hover seam, branched on the dragged window kind.** Rejected: the design session explicitly chose *no new guard predicate at the hover seam* — the three entry points already gate on `drag_state.is_some()`, so anything that occupies `drag_state` is suppressed for free. Adding a kind-branched guard there is exactly the parallel-logic smell the prior option also creates.
- **Pull floats into `drag_state` via a single `DragMode::Float` variant (chosen).** One variant covers both float translate (title-bar drag) and float resize for the whole move-size window — there is no behavioral split, since both just write the rect back. The variant carries only the float's `WindowId` and raw HWND so `drag_state.dragged_hwnd()` can route the float's `LOCATIONCHANGE` events into the drag path. Tiles behave exactly as before; programmatic float changes (which do not fire `MoveSizeStart`) stay on the passive sync path, unaffected.

## Consequences

- **The drag-module boundary is reversed.** The `drag.rs` module doc and `docs/src/dev-guide/tile-drag.md` previously stated "floating windows never enter `DragMode`"; both now record that floats enter `DragMode::Float` on a `Floating`-hwnd `MoveSizeStart`. A future reader who re-introduces the early-return for floats reintroduces the exact FFM-steals-foreground bug behind #24. This reversal is deliberate.
- **The float variant owns live rect-sync.** Because `LOCATIONCHANGE` events are routed in `run.rs` by `drag_state.dragged_hwnd()`, a float that occupies `drag_state` stops routing to the passive float-sync path and routes to the drag-move handler instead. `DragMode::Float`'s move handler therefore calls the existing `FlowWM::store_float_rect` (defined in `src/daemon/floating_sync.rs`, the same logic the passive path uses) so the stored float rect keeps updating live — no regression from today's passive float-sync behavior. Identity alone is carried; no `start_rect` and no grip edges are tracked.
- **The float variant skips `Classifying` and performs no layout commit on release.** Tiles enter via `Classifying` and are promoted to translate/resize by a cursor-vs-rect hit-test at the first `LOCATIONCHANGE`. Floats have no layout to commit and no translate/resize distinction, so they enter steady-state directly on `MoveSizeStart` and clear `drag_state` on `MoveSizeEnd` with no commit — the final rect was already synced on the last `LOCATIONCHANGE`. This is the same free-during-drag / commit-on-release split ADR-0004 documents for tiles, with the commit half intentionally empty for floats.
- **Lifecycle is `MoveSizeStart`-gated only.** `DragMode::Float` is entered exclusively on a `Floating`-hwnd `MoveSizeStart` and exited on `MoveSizeEnd`. Programmatic float changes (animations, layout-driven moves) do not fire `MoveSizeStart` and stay on the passive sync path. The float remains in the Float layer throughout the gesture — the stacking invariant from [ADR-0003](0003-float-tile-stacking-invariant.md) is preserved while FFM is suppressed.
- **Accepted parity risk: no stuck-state watchdog.** If `MoveSizeEnd` is never delivered (hook miss, app crash mid-gesture), `drag_state` sticks and FFM stays off until restart. This is the identical latent risk the tile path already carries; the decision accepts parity rather than introducing new recovery machinery (see #24 "Out of Scope"). A future stuck-state watchdog, if added, would naturally cover both variants because they share the one `drag_state` field.
