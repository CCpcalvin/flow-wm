# Float-on-top stacking invariant: floats TOPMOST while flow owns the foreground, dropped otherwise

> **Revision.** The original decision (raise-then-restore via `SetWindowPos` seat-above in the focus sink) was **disproved by the #2 spike**: `SetWindowPos` succeeds but cannot keep a normal app window above the *foreground* window — Windows re-asserts the foreground on top (validated against `debug.log` + Win32 docs/SO). This revision records the pivot to a **TOPMOST toggle**, backed by PowerToys Always-On-Top as first-party prior art.

Floating windows are kept `WS_EX_TOPMOST` **while flow owns the foreground**, and dropped to non-topmost the moment the foreground moves to a fullscreen app or any non-flow window. The invariant is enforced in `on_focus_changed` — the single sink for all foreground changes — and re-evaluated on the foreground window's own resize (so F11 in any app is caught). "Focus" and "raise" stay distinct vocabulary (`CONTEXT.md`): focusing a tile gives it input + active border + scroll-to-reveal; the float simply stays on top because it is TOPMOST, not because it was re-seated. This ships **always-on, with no configuration knob.**

## Context

`SetForegroundWindow` bundles active state, keyboard focus, and a raise to the top of the Z-order. flow-wm had no concept of stacking layers — the only Z-order mutation anywhere was `SetForegroundWindow` — so focus-follows-mouse focusing a tile under (or overlapped by) a float raised the tile and buried the float. The same path broke native float resize: FFM is live during a window's move-size gesture (suppressed only for flow's own tile `drag_state`), so a cursor slipping off a float's resize edge raised the adjacent tile mid-grip. Every established tiling WM (i3, Hyprland, niri) separates a float layer from a tile layer; the hard part is realizing that on Win32, where flow sits *on top of* an OS that owns the focus/Z-order conflation. The #2 spike established empirically that the naive realization (raise-then-restore) does not work on Windows — see Considered Options.

## Considered Options

- **Raise-then-restore in the focus sink (`SetWindowPos(float, tile, SWP_NOACTIVATE)`).** **Disproved by the #2 spike.** The call returns success yet the float does not stay above the foreground tile — Windows re-asserts the foreground on top. flow's own border overlays *do* sit above the foreground, but only because they are created `WS_EX_NOACTIVATE | WS_EX_LAYERED | WS_EX_TOOLWINDOW` (a non-competing window); a normal managed app has none of those styles. `HWND_TOP` / seat-above is documented as unreliable above the active window. Reverted.
- **Focus-without-raise via `AttachThreadInput` + `SetFocus`.** Rejected: `SetFocus` does not fire `EVENT_SYSTEM_FOREGROUND` (breaks the single-sink side-effect chain unless duplicated into a second path), and it leaves the tile *focused-but-inactive* — Chromium-based apps (Chrome, Edge, VS Code, Electron) **throttle rendering and timers** when their window is not active (`WM_ACTIVATE`), so the window you're typing into would lag; clicks also re-activate and re-raise the tile, burying the float anyway.
- **Floats always `WS_EX_TOPMOST`.** Rejected as-is: an always-topmost float covers fullscreen apps (fullscreen video, borderless games) and other applications' windows — confirmed by the user's prior experience and by PowerToys Always-On-Top having the same limitation (its issue #27088).
- **TOPMOST toggle (chosen).** Floats are TOPMOST **iff the foreground is a flow-managed window and not fullscreen**; otherwise non-topmost. This is the mechanism Microsoft's own first-party PowerToys Always-On-Top uses (plain `SetWindowPos(HWND_TOPMOST)`), generalized: PowerToys only opts out via Game Mode, whereas flow opts out for *any* fullscreen/non-flow foreground — strictly more polite. TOPMOST is the only reliable way to keep a window above the foreground on Windows, so this is the sanctioned path.
- **Geometric dead-band widening each float's hit-region.** Rejected as a primary fix (only helps near float edges). The resize half of the problem has a cleaner fix (see Consequences).

## Consequences

- **Toggle in the focus sink.** `on_focus_changed` evaluates the live state — is the new foreground flow-managed and not fullscreen? — and sets all floats TOPMOST or non-topmost accordingly. A no-op when no floats exist. This preserves the single-sink architecture (the toggle replaces the dead seat-above reconciliation).
- **Fullscreen detection must be live and geometry-based, not state-based.** flow already classifies `Ignored(Fullscreen)` and re-runs it on `EVENT_OBJECT_STATECHANGE`, but pressing F11 in a browser/VS Code/terminal resizes the window → `EVENT_OBJECT_LOCATIONCHANGE`, not a state change — so the stored `Ignored` state misses it. The toggle therefore calls the existing live geometry+style check (`is_fullscreen`: covers the full screen *and* no caption/thick-frame) directly, on both the foreground change **and** the foreground window's own resize. The no-chrome clause correctly excludes maximized windows (they keep chrome), so an auto-hide taskbar does not cause false positives. Known heuristic limits to harden later: exact-rect match can miss ±1px offsets (a coverage tolerance is more robust), and it is primary-screen only today.
- **TOPMOST must be re-asserted, not set-once.** PowerToys re-pins on `EVENT_OBJECT_FOCUS` because topmost drifts (other apps grab topmost, events reset it — their issues #19168, #17332). flow inherits this requirement: a re-assertion pass on focus events keeps floats reliably above tiles over time.
- **Toggle flicker at boundaries is inherent.** Each transition (tile → fullscreen, flow → non-flow) has a brief window where floats are in the wrong state before the hook corrects — a flash. Mitigated by toggling synchronously in the hook; accepted as the cost of the approach (PowerToys avoids it only by not toggling at all).
- **Focusing a tile while floats are up** looks different from plain Windows: the focused tile is fully active (taskbar, borders) but floats remain visually on top. Deliberate, matches i3/Hyprland, but is the one behavior a Windows-native user may find surprising.
- **Native float move/resize is handled complementarily and independently:** `EVENT_SYSTEM_MOVESIZESTART`/`MOVESIZEEND` set a gesture flag that gates the hover poll (a twin of `drag_state`), so FFM cannot fire mid-resize. This does not touch the stacking invariant; it removes the other trigger that buried floats.
- **Privileged windows remain unmanageable.** A float running at a higher integrity level than flowd (elevated / `uiAccess` / UWP) cannot be `SetWindowPos`-ed — `ERROR_ACCESS_DENIED` (observed in `debug.log`; PowerToys shows the same UIPI wall and warns the user). Managing such windows needs flowd elevated or `uiAccess` (code-signing) — a separate capability, out of scope for this invariant.
