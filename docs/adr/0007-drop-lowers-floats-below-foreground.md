# Drop lowers floats *below the foreground*, not merely clears TOPMOST

**Status:** Accepted — supersedes the drop-mechanism half of [ADR-0003](0003-float-tile-stacking-invariant.md) (the "drop = clear `WS_EX_TOPMOST`" wording). ADR-0003's *invariant* (floats are TOPMOST while flow owns the foreground, dropped otherwise) still holds; only the *mechanism* for "dropped" is corrected here.

## Context

ADR-0003 ships a TOPMOST toggle: floats are pinned `WS_EX_TOPMOST` while the foreground is flow-managed, and "dropped" when the foreground is a fullscreen app or any non-flow window. The drop was implemented as a single `SetWindowPos(float, HWND_NOTOPMOST, …)` per float — i.e. *clear the topmost flag*.

That is **not sufficient**, and it was disproved empirically. `HWND_NOTOPMOST` does not sink a window behind the foreground; it places the window at the **top of the non-topmost Z-order band**, which sits *above* any non-topmost foreground. A fullscreen browser (Chrome) is non-topmost, so after the "drop" the float remains stacked above it. Confirmed against `debug.log`: clicking the HTML5 fullscreen button produced a correct live `is_fullscreen` verdict, a correct `Drop` decision, and a *successful* `SetWindowPos(HWND_NOTOPMOST)` — yet the float stayed visibly on top of the fullscreen video. The detection logic was right all along; the drop *action* left the float in the wrong band.

There is also no Win32 primitive to "place a window just below window X": `SetWindowPos(A, B)` seats A *above* B (the existing `Border::seat_above_target` relies on this). So lowering a float below a specific foreground cannot be expressed as a single targeted seat; the foreground must end up above the float by some other means.

## Considered Options

- **Lower the float to the absolute bottom on every drop (`HWND_NOTOPMOST` then `HWND_BOTTOM`).** Self-contained — only windows flow owns are repositioned, never the user's foreground app. Rejected as the *universal* mechanism: for a **non-flow** foreground that does not cover the screen (Task Manager, a dialog), bottoming the float sinks it below every tile too, so all floats vanish the moment focus lands on an ignored app. Bad UX, surfaced during the design session.
- **Re-raise the foreground on every drop (`HWND_TOP` after demoting the float).** `SetWindowPos(foreground, HWND_TOP, NOACTIVATE|NOMOVE|NOSIZE)` pushes the focused app back above the demoted float, giving `foreground > float > tiles` — correct for both kinds, and the float stays visible for a small non-flow app. Rejected as the *universal* mechanism because it performs a Z-order op on a window flow may not own (a foreign foreground), which is exactly the class of foreground-adjacent manipulation ADR-0003 treated with caution.
- **Two-mechanism drop, branched on the foreground kind (chosen).** A **fullscreen** foreground should fully hide the float, so the float is demoted and sent to `HWND_BOTTOM` (self-contained; the app covers the screen anyway). A **non-flow** foreground should *yield* the float without hiding it, so the float is demoted and the foreground is re-raised to `HWND_TOP`, leaving the float above the tiles but below the focused app. Each kind gets its correct outcome; the fullscreen path never touches the foreign app, and the foreign-app op is confined to the non-flow path.

## Consequences

- **"Drop" is redefined as demote-and-lower, not demote-only.** The `CONTEXT.md` stacking glossary captures this: `drop` = clear `WS_EX_TOPMOST` *and* lower below the foreground (bottom for fullscreen, behind-the-foreground for non-flow). A future reader who deletes the second `SetWindowPos` reintroduces the exact bug this records.
- **The drop mechanism branches on the already-computed `is_fullscreen`.** The pure decision (`Pin` / `Drop` / `NoOp`) is unchanged — it answers only *whether* to drop. The Win32 *how* (bottom vs re-raise) lives in the reconcile wiring, where `is_fullscreen` is already known. Pure unit tests stay valid.
- **Borders lower in lockstep.** A float's `Border` overlay is toggled `WS_EX_TOPMOST` while its float is pinned; on drop it is demoted and re-seated just above its (now-lowered) float via the existing `seat_above_target`, so the resize ring never dangles above a fullscreen app. `seat_above_target` seats the overlay above the float, which — once the float is below the foreground — leaves the border below the foreground too.
- **The non-flow re-raise operates on a window flow may not own.** This is the deliberate, documented cost of correct non-flow behavior. It is bounded: `NOACTIVATE` means no focus/activation steal; `HWND_TOP` only restores the foreground to the top of its band (going *with* Windows' own foreground preference, unlike the seat-*above*-foreground that ADR-0003's #2 spike disproved); and it **fails soft** — an elevated foreground (`Taskmgr`, `uiAccess`) denies the call with `ERROR_ACCESS_DENIED`, leaving the float above it. That is the same UIPI wall ADR-0003 already accepts for elevated floats, not a new limitation. The call site carries a `SAFETY`/doc comment recording this so it is not "cleaned up."
- **The fix is stable across animation.** The animator repositions windows with `SWP_NOZORDER` (Z-order preserved), so a lowered float is not bumped back up by the next animation frame. Lowering is also idempotent: once the foreground is correctly above the float, re-evaluation is a `NoOp`, so any hook event the re-raise happens to fire converges in a single pass (no busy-loop).
- **Exit restore is unchanged.** When focus returns to a flow window, `Pin` re-applies `HWND_TOPMOST`, promoting the float (and its border) back above everything — the existing path, no new restore logic.
