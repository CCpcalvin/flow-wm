# Event broadcast: consumer-owned named pipe, semantic Events

External applications (status bars like yasb) receive flow-wm state changes over a **subscriber-owned named pipe**: the subscriber creates `\\.\pipe\<name>`, registers it via a new `flow subscribe <name>` command, and the daemon opens that pipe as a `File` and pushes newline-delimited JSON **Events** to it. The existing command pipe (`\\.\pipe\flow`, one-shot request/response, `src/ipc/transport.rs`) is untouched. Events are **semantic state changes** (`workspace_changed`, `focus_changed`, `viewport_scrolled`, `tile_state_changed`, `window_moved_to_workspace`, `application_exiting`) plus a one-shot `state_snapshot` pushed on subscribe — never raw `HookEvent`s. This mirrors komorebi's named-pipe subscription model, not glazewm's WebSocket model.

## Context

flow-wm has no outbound state-change channel today. The daemon owns all state on the main thread (`src/daemon/types.rs`), serves exactly one command-pipe client at a time, and `DisconnectNamedPipe`s after every response (`src/ipc/transport.rs`); the `flow` CLI is one-shot (connect → send → read → drop). The hook thread forwards raw OS signals (`HookEvent` — `SystemForeground`, `ObjectCreate`, `MoveSizeStart`, …) through an mpsc channel that the main thread drains between IPC messages; there is deliberately no `Arc<Mutex>` and no shared state (`CLAUDE.md`). Any event-broadcast design must fit this model: outbound writes on the main thread, no new concurrency, no long-lived inbound connection that would block the one-shot command pipe. The reference Windows tiling WMs split sharply here — komorebi has the *consumer* create a named pipe and the WM write to it (`SUBSCRIPTION_PIPES: HashMap<String, File>`); glazewm runs a multi-client WebSocket server (`127.0.0.1:6123`) with long-lived connections and per-subscriber async tasks. Only the former is compatible with flow-wm's threading invariant.

## Decision

- **Consumer-owned pipe (Option B).** Subscriber creates its pipe; `flow subscribe <name>` registers it. The daemon holds a list of subscriber `File`s on the main thread and writes each Event to all of them. The command pipe stays one-shot and sequential.
- **Events are semantic, payload-rich, tagged.** `#[serde(tag = "type", rename_all = "snake_case")]` on the `Event` enum — the enum *is* the wire schema. Each variant carries enough to render (monitor, workspace, window `{hwnd,title,exe,class}`, viewport offset/column count, tile/float state). Adding an event = one variant + one emit call; consumers ignore unknown `type` (forward-compatible).
- **Seven variants.** Five state changes (`WorkspaceChanged`, `WindowMovedToWorkspace`, `FocusChanged`, `ViewportScrolled`, `TileStateChanged`), plus `StateSnapshot` (once per subscriber, on subscribe) and `ApplicationExiting` (on graceful shutdown).
- **`StateSnapshot` = the `QueryState` payload, pushed.** On subscribe the daemon emits one `state_snapshot` so the subscriber can first-paint without implementing an explicit query. One serializer, two callers (the `flow query` pull and the subscribe push).
- **`move-to-workspace` emits both** `WorkspaceChanged` and `WindowMovedToWorkspace`. The camera follows the moved window (`dispatch_move_window_to_workspace` → `switch_active_workspace`, `src/daemon/dispatch.rs`), so the active workspace genuinely changes; a subscriber tracking only "current workspace" must not miss move-driven switches, so `WorkspaceChanged` fires whenever the active workspace changes regardless of cause, and the move event carries the relocation detail (`{window, from, to}`).
- **Subscribe lifecycle.** `Subscribe { pipe_name }` IPC message → daemon opens `\\.\pipe\<name>` as a `File`. Every write error silently evicts that subscriber (never blocks, never panics) — a dead/blocked subscriber pipe cannot stall the WM. `ApplicationExiting` is emitted to all subscribers before teardown. Relaunch detection is **subscriber-side**: the daemon is dead during the gap, so on EOF the subscriber enters a reconnect loop, retries `flow ping` then `flow subscribe`, and the fresh `StateSnapshot` re-inits it. `ping` is side-effect-free.
- **ViewportScrolled is flow-wm-unique.** The infinite horizontal canvas + sliding viewport (`ScrollingSpace`) has no analogue in komorebi/glazewm; the scroll event is designed from scratch.

## Considered Options

- **glazewm's WebSocket model (WM-owned server, long-lived connection).** Rejected: it requires keeping connections open and serving multiple clients concurrently, which means rearchitecting the accept loop away from one-client-at-a-time and straining the no-`Arc<Mutex>` / main-thread-owns-all-state invariant (N live connections each want a writer the main thread feeds). A bar holding the single command pipe open would block every `flow` CLI hotkey. komorebi's outbound-write model avoids all of this.
- **Publish raw `HookEvent`s.** Rejected: raw OS signals (`SystemForeground`, `ObjectCreate`, …) are noisy Win32 noise; a subscriber would have to reverse-engineer flow-wm internals to learn anything. Events are derived semantic state changes, decoupled from hook signals (not every `HookEvent` becomes an `Event`; some `Event`s, like viewport scroll, are not driven by a single hook signal at all).
- **Window managed/unmanaged events (komorebi/glazewm vocabulary).** Rejected: those WMs *take over* window placement, so a window is "managed" or not. flow-wm floats every window by default and only orchestrates — Win32 always owns the window; the manage/unmanage concept does not apply.
- **Generic `WorkspaceUpdated` on contents mutation.** Rejected: a window moving between workspaces would fire two generic contents-mutation events. Replaced by the single, operation-level `WindowMovedToWorkspace { window, from, to }` — self-contained, one event tells the subscriber everything.
- **Notification-only events (re-query on every change).** Rejected: payload-rich events avoid a `flow query` round-trip after every change and race on rapid switches. The cost is serialization on the main thread, which is fine — events fire at human-interaction rate, not per-frame.
- **Replay existing events on subscribe instead of a `StateSnapshot` variant.** Rejected: replaying current `WorkspaceChanged` + `FocusChanged` + `ViewportScrolled` works (computed from current state, not a stored log) but gives the subscriber no way to distinguish bootstrap from a live change, and spreads init across three lines. A single `StateSnapshot` (== `QueryState` payload) is one explicit bootstrap message reusing the existing query serializer.
- **Per-message full-state embedding (komorebi's `state` sibling on every event).** Rejected: snapshot-once beats snapshot-every-time; per-message state bloat with no benefit once the subscriber has initialized.
- **`ping` health-check command.** Accepted for v1: trivial, side-effect-free, cleanly separates "is the daemon up?" from "register me as a subscriber" in the reconnect loop. (komorebi/glazewm skip it and retry-subscribe; flow-wm ships it anyway.)

## Consequences

- **Additive only — no rearchitect.** The command pipe, the accept loop, the hook-thread/`HookEvent` channel, and the `FlowWM` ownership model are all unchanged. The subscriber list is one more field the main thread owns; event emission is one more outbound write per state change, routed through the main thread alongside the existing hook-event drain.
- **Extensibility is the wire contract.** The `Event` enum is the schema. A future event (e.g. `MonitorChanged`, `WorkspaceUpdated` for non-active contents, config-reload) is one variant + one emit call site; existing subscribers keep working because they ignore unknown `type` values.
- **Subscriber owns reliability, not the daemon.** The daemon's entire lifecycle obligation is two events: `StateSnapshot` on (re)subscribe and `ApplicationExiting` on graceful exit. Crash recovery is implicit — a crash drops the pipe, the subscriber sees EOF, same reconnect path as a graceful exit. The daemon never knows whether a subscriber is "new" or "reconnecting."
- **New IPC surface.** `Subscribe { pipe_name }` message + `flow subscribe <name>` CLI verb + side-effect-free `Ping`/`flow ping`. The subscriber pipe name is chosen by the subscriber (least coupling; yasb uses whatever it expects), not dictated by flow-wm.
- **`flow query` and `state_snapshot` share a serializer.** The queryable state has one shaping function; `flow query` returns it synchronously, subscribe pushes it once. No duplicate state-shaping logic to keep in sync.
- **Write-error eviction is load-bearing.** A subscriber that dies, blocks, or whose pipe fills must not freeze the WM. Writes that fail (broken pipe, full buffer) evict the subscriber silently — this is the invariant that keeps event publishing from ever regressing the WM's responsiveness.
